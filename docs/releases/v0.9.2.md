# SI-Coder v0.9.2

SI-Coder v0.9.2 hardens the boundary between a simple user-facing `sc` tool and the engineering machinery behind it. The release focuses on first-run credential isolation, capability truthfulness, release integrity, repository-wide secret scanning, GitHub PAT diagnostics, current MCP compatibility, and tested Node support.

## First-run credentials are connection-scoped

Fresh local setup no longer starts by writing provider credentials into `~/.bashrc`.

```text
install
  → SI-Coder user
  → provider
  → named connection
  → hidden credential input
  → 0600 connection store
  → doctor
```

`sc setup` creates/selects a user, creates a direct named connection for each selected active provider, and writes values only to that connection's private store. Existing legacy profile values are migrated locally when applicable. Legacy shell/profile flows remain explicit compatibility paths rather than the default onboarding architecture.
The historical `si-coder-onboard` executable name is preserved, but now delegates to the same safe `sc setup` flow. The old shell-export wizard is retained only as the explicit `bin/onboard-legacy.js` compatibility path.

## Unfinished capabilities fail closed

`skills/catalog.json` is the lifecycle SSOT for default installation. Active/default skills are installed; unfinished and legacy skills remain in the repository for maintenance/backward compatibility but are not normal routing targets.

Dedicated automation that remains unfinished:

- `sc-resend` provisioning automation (credential status/doctor remains available in `sc-provider`);
- `sc-stripe`;
- `sc-clerk`;
- `sc-supabase`.

Cloudflare DNS is explicitly active. Its onboarding guidance now requests only `Zone:Read` + `Zone:DNS:Edit` for the implemented DNS capability instead of presenting Cloudflare as a generic stub.

## Release integrity

A pushed `v*` tag no longer goes directly to publication. The release workflow now:

1. checks out the exact tag with full history;
2. verifies tag ↔ package version ↔ release note alignment;
3. proves the tag commit is on `origin/main`;
4. runs `npm run verify:release` again;
5. regenerates deterministic artifacts and rejects drift;
6. verifies `sc.zip` and `sc.skill` are byte-identical siblings;
7. optionally publishes the verified npm fallback independently of GitHub public visibility;
8. verifies the repository and tagged source are anonymously reachable before attempting a GitHub Release;
9. creates or repairs the GitHub Release idempotently;
10. generates GitHub artifact attestations for release assets when the repository is public;
11. verifies the actual `sc.zip` release asset is anonymously downloadable before declaring GitHub distribution healthy.

The workflow can be manually rerun for an existing tag after an external GitHub visibility problem is resolved. `npm version` no longer has an automatic `git push --follow-tags` lifecycle hook. npm publication runs before the public-GitHub reachability assertion so a configured registry token can provide a fallback even while GitHub visibility is externally restricted.

GitHub Actions dependencies are pinned to immutable commit SHAs, a package lockfile is committed, CI installs with `npm ci`, and Dependabot monitors GitHub Actions/npm metadata.

## Repository-wide secret scan

Release verification now scans the repository checkout rather than only `.agent/`. It includes tracked and untracked text files that could accidentally enter source/generated packages, skips VCS/dependency caches and binary/large artifacts, and continues to reject secret-shaped memory/evidence writes separately.

## GitHub classic PAT diagnostics

Direct GitHub remains PAT-classic-only (`classic-pat`, `ghp_…`). Doctor now inspects GitHub's classic-token scope metadata when available:

- `repo` → private + public repository automation;
- `public_repo` → public repositories only;
- neither → repository-write capability is considered insufficient.

A GitHub SAML SSO block is surfaced separately. When `GH_OWNER` targets a different organization/account, doctor explains that organization PAT policy or SSO authorization can still gate repository operations even when token identity/scopes look valid.

## MCP 2026-07-28 + legacy compatibility

The dependency-free stdio MCP adapter now supports both eras:

- **2026-07-28** — `server/discover`, stateless calls with per-request `_meta`, required wire `resultType` discrimination, cache hints for list results, and server identity metadata;
- **2025-11-25** — existing `initialize`/`initialized` compatibility for clients that have not migrated yet.

The machine function SSOT remains `machine/functions.json`; protocol compatibility does not duplicate tool schemas.

## Runtime support

SI-Coder now requires Node.js **22 or newer**. Node 18 is EOL and the repository's current test infrastructure is not compatible with its older `node:test` MockTimers API. CI/release verification uses Node 22 and compatibility jobs cover newer supported Node majors.

The local installer validates Node before installation, installs only active/default skills from the catalog, and no longer hides `npm link` failures.

## Public distribution boundary

Git SSH/tag publication and public availability are treated as separate facts. A tag may exist while an account/repository visibility restriction makes public GitHub/raw/release URLs return 404. The release workflow therefore refuses to claim/publicize a GitHub Release until unauthenticated reachability succeeds. Optional npm publication can run when a repository `NPM_TOKEN` is configured; absence of that secret does not fake an npm release.

## Verification

`v0.9.2` is gated by targeted first-run/auth/MCP/distribution tests, full regression, docs/version synchronization, lifecycle catalog validation, deterministic generated artifacts, repository-wide secret scan, strict skill verification, Node compatibility checks, and git diff review.
